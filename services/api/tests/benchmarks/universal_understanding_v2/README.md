# Universal Understanding Benchmark V2

Files nobody has tuned Smart Import on. The official benchmark (`tests/benchmarks/smart_import_v3`, 240 documents) is the regression
guard; this one asks a different question: *how much of a never-seen CSV/XLSX does NINFA understand on the first upload, and does it ever
claim more than it should?*

```
python -m tests.benchmarks.universal_understanding_v2            # from services/api; ~10 minutes
python -m tests.benchmarks.universal_understanding_v2 --groups costs --split dev --repeats 1 --no-stages --no-probes
python -m tests.benchmarks.universal_understanding_v2.compare BEFORE.json AFTER.json
```

Nothing is read from or written to a database, nothing leaves the process, no model is called (`IMPORT_UNDERSTANDING_PROVIDER=unconfigured`).

## The corpus (402 documents)

| Group | Documents | What it is |
|---|---|---|
| bookings | 120 | PMS / channel-manager / front-desk exports (`gen_bookings.py`) |
| labor | 120 | staff rosters, timesheets, day grids (`gen_labor.py`) |
| costs | 120 | purchase registers, ledgers, multi-line invoices (`gen_costs.py`) |
| negative | 27 | real office spreadsheets that are none of the three: inventory, trial balance, restaurant takings, marketing, web analytics, contacts, to-do list, rules, menu - each uploaded on the three cards |
| unsupported | 15 | PDF, text, old .xls, .xlsm, UTF-16 text, empty file, broken archive, a workbook named .csv, HTML as .xls, binary, **pipe-delimited files** |

Each positive group has 30 EASY, 40 MEDIUM, 30 HARD and 20 ADVERSARIAL documents. Documents are **generated from recipes**, deterministically
(a document depends on its id alone), and no two are byte-identical. None is a document of the official corpus.

## The truth is written next to the file

Never read from Smart Import and never derived from its vocabulary. A document is **READY** when a careful person, seeing the header, the values
and what surrounds them, would import it without asking anything. A header that is only part of a name ("Total", "Importo", "Data") over values that
cannot say more is not clear: the recipe says ASK and names the question and its answer. `validate()` reopens every generated file with
openpyxl / csv - never with Smart Import's readers - and checks the truth against it.

Two truth decisions were taken *after* the first runs, because the truth conflicted with a product decision already merged (recorded here so they
are not mistaken for tuning to the engine):

* the names of people under a supplier header are asked about, not refused (official case C45 reads a sole trader's name as a supplier);
* a pipe-delimited file is an unsupported file (the delimiter set is a tested contract), not a READY one.

And corrections of the benchmark's own mistakes: a commission *amount* is revenue x rate (not the rate); a hidden-sheet document carries no table facts
(the product deliberately does not read hidden sheets); `Trasporti` is a clear NINFA category (`TRANSPORT`); booking numbers do not restart in every
monthly sheet.

## Metrics

Per kind of data and per difficulty, on the **positive** documents only; negatives and unsupported files are scored apart (did Smart Import stay out
of the way: no automatic import, no exception).

* **Strict** domain / header / table accuracy: a document the engine could not read at all counts as a miss (the official figures skip it).
* **Required precision / recall**, **optional precision**; **critical wrong mapping**; **false automation**; **zero-question rate** (of the documents
  that are clear); **necessary-question recall**; unnecessary questions; **personal data** (values shown or sent, columns not excluded).
* **Performance** per file, per stage: workbook scan, semantic mapping (`propose`), the rest of the understanding, total (mean / p50 / p95 / max).

## Anti-overfit

* every document is classified `dev` or `holdout` by the hash of its id (`--split`). The engine was improved looking at `dev` failures only; `holdout`
  was measured at the end. The first vocabulary pass for **bookings** was derived from the failure list of the whole bookings baseline, so for that
  group the split is only partially independent (disclosed in the report).
* a few holdout failures were fixed after the holdout run (five header words, a rule about a group code, a commission "after" word, the net of a line in
  a multi-line invoice). They are listed in the report; the holdout figures quoted there are the ones measured **before** those fixes.
* every rule added has its counter-example in `tests/test_universal_understanding_headers.py`; `sabotage` runs (rule broken, tests that fail, metric
  that worsens) are in the report.

## What the corpus does not claim

It is generated by the same person who improved the engine. Header vocabularies come from reading what PMS exports and hand-made sheets look like, not
from a sample of a customer's files, so the figures are a measure of *breadth on plausible unseen files*, not a promise on every real export.
