# NINFA — Priority Engine v1 (Gate 10)

Cross-domain signal ranking over the five MVP detectors. It answers exactly one question:

> "Of everything a detector already said is TRIGGERED right now, what should be looked at first?"

**It does not decide whether a detector is right.** That decision belongs entirely to the
detector (Gates 5, 7, 8, 9); the Priority Engine normalizes and orders what is already TRIGGERED,
never re-derives it. Code: `services/api/app/modules/intelligence/priority/`. Entry point:
`PriorityService.rank(context, evaluations)`. No table, migration, API endpoint, worker task or
dependency was added; the head stays `0008_labor_ingestion`.

    TRIGGERED EVALUATIONS -> NORMALIZED PRIORITY COMPONENTS -> PRIORITY SCORE -> RANKING

## Triggered-only

`PriorityService.rank()` accepts an evaluation of *any* status, but only `TRIGGERED` becomes a
`PriorityCandidate`. Every other status is excluded and **counted**
(`excluded_clear_count`/`excluded_insufficient_count`/`excluded_not_applicable_count`/
`excluded_suppressed_count`) — never scored, never given a rank at the bottom of the list. In
particular, `SUPPRESSED_LOW_CONFIDENCE` is never "resuscitated" here: a detector that decided it
was not confident enough to show a signal stays unshown, however large its underlying numbers are.
If nothing is `TRIGGERED`, the ranking is legitimately empty (`candidate_count = 0`,
`ranked_candidates = ()`) — this is not an error and nothing is invented to fill it. A future UI
may translate an empty ranking into "everything is under control"; that translation never happens
here, and no text is generated by this gate at all.

## Why Impact is NORMALIZED OPERATIONAL SEVERITY, not euro

Impact V1 is **never** a currency amount, a revenue loss, a saving or a profit figure. Three
reasons: not every detector has an economic proxy at all (OTA has none in this document's sense —
its optional revenue *exposure* is evidence, not a scoring input); the four detectors that do have
one use different currencies, so directly comparing them would silently rank whichever property
happens to have a stronger local currency or larger absolute numbers; and some proxies are
themselves *gross exposure* figures (never a loss), so scoring on them would smuggle a false
precision into the ranking. Impact instead asks: *how far past this detector's own already-decided
threshold does this signal sit*, mapped onto one common 0-100 scale so a percentage-point gap, a
room count, an hour count and a cost ratio become genuinely comparable severity.

## `threshold_progress`: the one shared shape

```
threshold_progress(value, threshold, saturation) -> 0..100

    value <= 0                      -> 0
    0 < value < threshold           -> linear 0 -> 50
    value == threshold              -> 50
    threshold < value < saturation  -> linear 50 -> 100
    value >= saturation             -> 100
```

`threshold = 50` because the point a detector's own rule starts firing is the scale's own midpoint,
not an arbitrary mark: it lets the upper half (50-100) express "how far beyond the trigger" and the
lower half (0-50) express "how close to it", symmetrically. `saturation = 100` is a policy ceiling
(V1 does not track severity beyond it, not a claim that nothing worse exists); the convention is
`saturation = 2 x threshold` unless the value is itself a bounded percentage. Every operation is
`Decimal`, in the dedicated 50-digit context, never rounded before it decides anything.

## Impact per detector

| Detector | Components | Combined via |
| -------- | ---------- | ------------- |
| `REV_PICKUP_LOW` | `threshold_progress(abs(min(delta_percent_exact,0)), 20, 40)`; `threshold_progress(missing_rooms, 2, 4)` | **MIN** (the detector needs BOTH conditions: AND) |
| `REV_OCCUPANCY_RISK` | `threshold_progress(occupancy_gap_pp_exact, 10, 20)`; `threshold_progress(room_shortfall, 3, 6)` | **MAX** (the detector triggers on EITHER: OR) |
| `REV_OTA_DEPENDENCY` | structural: `threshold_progress(actual_share, 70, 100)`; rising: `MIN(threshold_progress(actual_share, 55, 100), threshold_progress(max(delta_pp,0), 15, 30))` | structural-only -> structural component; rising-only -> rising component; both -> **MAX** of the two (independent paths, the stronger one names the impact) |
| `COST_CPOR_ANOMALY` | `threshold_progress(max(delta_percent_exact,0), 20, 40)`; `threshold_progress(actual_cpor/upper_fence, 1, 1.5)` | **MIN** (all four numeric conditions are AND; the monetary `cost_gap_proxy` never enters — the ratio is currency-free) |
| `LABOR_OVERSTAFFING` | `threshold_progress(max(delta_percent_exact,0), 20, 40)`; `threshold_progress(excess_hours_exact, 4, 8)` | **MIN** (AND; the optional `labor_cost_gap_proxy` never enters) |

A `COST_CPOR_ANOMALY` evaluation with `upper_fence_exact <= 0` is `PRIORITY_INVALID_SOURCE_
EVALUATION`: a fence that cannot be a denominator is never given a fallback.

## Impact validation

A TRIGGERED evaluation's own boolean condition fields (`percent_condition`/`rooms_condition`,
`gap_condition`/`shortfall_condition`, `structural_condition`/`rising_condition`, the four cost/
labor conditions) are **read, never recomputed**: if they say the trigger did not really hold,
that evaluation is `PRIORITY_INVALID_SOURCE_EVALUATION`. This never "corrects" a detector; it
refuses to score something whose own facts contradict its own status.

## Urgency: how SOON, never how SEVERE

Three shapes, one per family of detector, all step functions of `Decimal` inputs (a pure function
needs no interpolation):

* **Forward-dated** (`REV_PICKUP_LOW`, `REV_OCCUPANCY_RISK`, `LABOR_OVERSTAFFING`) —
  `days_to_target = target_date - PriorityContext.as_of_local_date` (the stay date for revenue,
  the work date for labor). Bands: `0-1 -> 100`, `2-3 -> 90`, `4-7 -> 80`, `8-14 -> 65`,
  `15-30 -> 50`, `31-60 -> 35`, `>60 -> 20`. `days_to_target < 0` is
  `PRIORITY_STALE_SOURCE_EVALUATION`.
* **`REV_OTA_DEPENDENCY`** — a fixed policy, never a fabricated "days to the window" (the
  30-day forward window's *start* is not a deadline in the pickup/occupancy sense): `STRUCTURAL`
  only `-> 40`; `RISING` only or `STRUCTURAL + RISING` together `-> 60` (a share that is still
  moving needs a faster look than one that has simply been high for a long time).
* **`COST_CPOR_ANOMALY`** — retrospective: `days_since_period_end = PriorityContext.
  as_of_local_date - target_period_end`, which must be `>= 1` (the month must have concluded;
  `< 1` is `PRIORITY_INVALID_SOURCE_EVALUATION`). Bands: `1-7 -> 70`, `8-30 -> 55`, `31-60 -> 40`,
  `61-90 -> 25`, `>90 -> 10` (the anomaly is most actionable while the month's context is still
  fresh, and steadily less so as it ages).

## Source as-of coherence

A TRIGGERED evaluation's own as-of/snapshot date must equal `PriorityContext.as_of_local_date`
exactly, or `PRIORITY_AS_OF_MISMATCH`: `snapshot_local_date` for revenue, `target_as_of_date` for
labor, `as_of_local_date` for OTA. `COST_CPOR_ANOMALY` has no as-of field of its own (it is
retrospective by construction) so it has no such check; its own freshness rule is the urgency
section's `days_since_period_end >= 1`. The point of every one of these checks is the same: never
mix signals produced on different days into one "morning ranking".

## Confidence: reused, never recomputed

`confidence_score` is **exactly** the detector's own final confidence (0-100), copied, never
averaged, never transformed. Because only `TRIGGERED` evaluations reach this component, that
confidence must already be at or above the detector's own gate (50 for `REV_PICKUP_LOW`, 55 for
the other four); a `TRIGGERED` evaluation below its own gate, or a confidence outside `0-100`, is
`PRIORITY_INVALID_SOURCE_EVALUATION` — an internal-coherence check, not a re-decision.

## Actionability V1: a fixed heuristic policy

Not a probability, not a formula — a lookup table, versioned as `priority-actionability-v1`:

| Decision type | Score |
| ------------- | ----- |
| `REV_PICKUP_LOW` | 90 |
| `REV_OCCUPANCY_RISK` | 85 |
| `REV_OTA_DEPENDENCY` | 60 |
| `COST_CPOR_ANOMALY` | 70 |
| `LABOR_OVERSTAFFING` | 90 |

It says how directly a signal *can be* the object of an operational response, never what that
response should be: no action text ("lower the price", "cut a shift", "renegotiate the supplier")
is generated from it or anywhere else in this gate.

## Priority Score V1: the frozen formula

```
priority_score = 0.40 x impact + 0.25 x urgency + 0.20 x confidence + 0.15 x actionability
```

`IMPACT_WEIGHT = 0.40`, `URGENCY_WEIGHT = 0.25`, `CONFIDENCE_WEIGHT = 0.20`,
`ACTIONABILITY_WEIGHT = 0.15`, summing to exactly `1.00`; versioned as `priority-engine-v1`, never
a database row. Every component is `0-100`. `priority_score_exact` is the full-precision value
computed in the dedicated 50-digit `Decimal` context (`priority.precision`, re-exported from
Gate 5's own) and is what the **ranking sorts on**; `priority_score_display` (HALF_UP, two
decimals) is presentation only and never decides anything — two candidates 0.004 apart can display
identically and still rank in the order their exact scores say.

## Deterministic ranking and tie-break

Eight keys, all descending except the technical tie-break, applied in this order:

1. `priority_score_exact`
2. `impact_score_exact`
3. `urgency_score`
4. `confidence_score`
5. `actionability_score`
6. `decision_type`, by a **fixed, purely technical** order (`REV_OCCUPANCY_RISK`, `REV_PICKUP_LOW`,
   `LABOR_OVERSTAFFING`, `COST_CPOR_ANOMALY`, `REV_OTA_DEPENDENCY`) — it expresses no semantic
   superiority between detectors, only a stable last resort
7. `source_target_key`, lexicographically
8. `source_evaluation_fingerprint`

Every candidate gets a **unique** rank `1..n` (never dense or shared), and the input order of the
evaluations passed to `rank()` never changes the output order. `ranked_candidates` always holds
**every** candidate: there is no top-N truncation here — that is a presentation concern for a
later gate (a future Home NINFA can show a top 5 without this engine ever knowing what "5" means).

## Candidate and ranking result

`PriorityCandidate` (immutable, never persisted) carries: the decision type, the tenant scope, the
five scores (`*_exact` and `*_display` where applicable), `impact_basis`/`urgency_basis` (plain
data — every raw input the two scores were computed from, so a `TRIGGERED` candidate can be
audited without recomputing it), `actionability_policy`, an optional `economic_proxy_exact`/
`economic_proxy_currency`/`economic_proxy_label`, the source's own `reason_codes`, the priority
rules version and a `calculation_fingerprint`. `PriorityRankingResult` carries the tenant scope,
`candidate_count`, the four exclusion counts, `duplicate_input_count`, `ranked_candidates` (a
tuple of `(rank, candidate)`) and its own `calculation_fingerprint`.

## Economic proxy: evidence only, never scored, never compared across currencies

`revenue_gap_proxy` (pickup/occupancy), `cost_gap_proxy_exact` (cost, with its own `currency`),
`labor_cost_gap_proxy_exact` (labor, with its own `cost_currency`) and the optional OTA room
revenue exposure travel through as **evidence**, exactly as their own detector defined them (a
gross exposure, never a loss or a saving): they never enter `priority_score_exact` and are never
compared against another candidate's proxy, in any currency. Revenue's and OTA's own evaluations
carry no currency string at all (neither `Booking` nor `RevenueDecisionEvaluation`/
`OtaDependencyEvaluation` has one — only `Property.currency` does, and this engine never queries a
repository to fetch it), so `economic_proxy_currency` stays `None` for those two rather than
guessing one. No FX conversion is ever attempted anywhere in this gate.

## Determinism and fingerprints

Both a candidate's and a whole ranking's SHA-256 fingerprint are canonical JSON of the logical
content that decided the result — Decimals via `canonical_text` (non-lossy: two values on
opposite sides of a threshold never share a fingerprint even if they display alike) — and never a
runtime timestamp, a memory address, a row order or a display-only figure. A ranking fingerprint
is always built from the candidates in their **final rank order**, never the caller's input order,
so the same logical set of TRIGGERED evaluations gives the same ranking fingerprint whatever order
they arrived in.

## Duplicates and conflicts

Within one run, two `AdaptedSignal`s of the **same** `(decision_type, source_target_key)`:
identical `source_evaluation_fingerprint` -> the same evaluation seen twice, deduplicated to one
candidate and counted (`duplicate_input_count`); a **different** fingerprint ->
`PRIORITY_CONFLICTING_SOURCE_EVALUATION` (never chosen arbitrarily). Two different decision types
describing the same calendar date (`REV_PICKUP_LOW` and `REV_OCCUPANCY_RISK` on the same stay
date) are two distinct signals and are **never** merged — grouping is always by
`(decision_type, source_target_key)`, never by the target key alone.

## Validation and error codes

Every evaluation, of any status, must belong to `PriorityContext.workspace_id`/`property_id` or
the WHOLE run is rejected (`PRIORITY_TENANT_MISMATCH`/`PRIORITY_PROPERTY_MISMATCH`) — a mismatch is
never silently dropped or silently counted. `PRIORITY_INVALID_SOURCE_EVALUATION` covers an
unrecognised evaluation type, incoherent TRIGGERED facts, a confidence outside `0-100` or below
the detector's own gate, a malformed fingerprint and a cost period that has not concluded.
`PRIORITY_AS_OF_MISMATCH` and `PRIORITY_STALE_SOURCE_EVALUATION` are described above.
`PRIORITY_CONFLICTING_SOURCE_EVALUATION` is described above. Nothing here re-decides a detector's
own status.

## Performance and read-only

`PriorityService` takes **no** `Session` and **no** `TenantContext`: it never queries a repository,
never calls a detector and never recomputes a detector's own facts — it is a pure function of
already-computed evaluations. This is what makes it independently testable without a database at
all, and is why it can never accidentally re-run a detector. Zero SQL, zero ORM import, zero
write, anywhere in `intelligence/priority/`.

## Explainability

Every fact needed to audit a TRIGGERED candidate is a plain, typed value on it: which detector it
came from and why (the source's own `reason_codes`), the source target, the detector's own
confidence, the impact score and its raw inputs (`impact_basis`), the urgency score and its
temporal basis (`urgency_basis`), the actionability policy name, the exact priority formula's
four inputs, any economic proxy, the final rank and which tie-break key applied. None of this is
generated natural-language text.

## Limitations (intentional, V1)

* The four weights (40/25/20/15), the actionability table and the urgency bands are product
  heuristics that need calibration with real customers; they are versioned constants in code, not
  database settings.
* Impact V1 deliberately ignores every economic proxy: a future version that wants to blend
  severity with an FX-normalized, risk-adjusted exposure figure is a new, explicitly versioned
  policy, not a silent change to this one.
* No priority is persisted, no lifecycle, no deduplication across days, no Decision Memory, no
  recommendation, no AI/ML ranking model, no business API, no UI, no worker/scheduler: all belong
  to a later gate, on top of this one, unchanged.
* A whole-property event that makes several detectors trigger together is visible only as several
  separate, correctly-ranked candidates — V1 has no notion of one signal explaining another.
